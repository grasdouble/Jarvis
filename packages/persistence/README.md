# PostgreSQL persistence

`@jarvis/persistence` contains the PostgreSQL schema, core-owned lease-bound checkpoint and task-result adapters, and durable queue store. It accepts a pool implementing `SqlPool`; service startup remains responsible for configuring the PostgreSQL driver and connection credentials.

## Migration lifecycle

Call `PostgresPersistence.migrate()` once during controlled deployment, using a dedicated migrator connection. Migration execution is serialized with a PostgreSQL advisory lock, applied in transactions, and recorded with SHA-256 checksums. An applied migration is immutable; add a new numbered migration rather than editing one already recorded. The migrator needs schema/table creation privileges and `CREATEROLE` for the initial `jarvis_app` and `jarvis_agent` role setup. Do not use the runtime service login as a database superuser or migrator.

After migration, grant the runtime login membership in `jarvis_app` through deployment configuration. `jarvis_app` is a non-login role with no `DELETE` privilege and no `UPDATE` privilege on append-only configuration, policy, revision, checkpoint, task-result, report, evidence, skill-consent, decision, knowledge-version, or audit records. `jarvis_agent` is a non-login role with no schema grants; agent/model containers receive no database connection or database credentials. Database roles are an additional boundary, not a substitute for deterministic core validation.

The migration does not store provider credentials, raw provider sessions, prompts, or agent login material. Project-scoped composite foreign keys keep task, request, configuration, result, report, and checkpoint references within the same repository identity. Numeric GitHub identities use `bigint`; clients must serialize them as strings where JavaScript precision could be lost.

## Local owner authentication

Migration `005_owner_auth` adds one singleton owner credential and server-side session rows. `PostgresOwnerAuthStore` persists only the password hash, session-token digest, CSRF-token digest, inactivity timestamps, and revocation state. The API receives the one-time onboarding secret from trusted startup configuration; the secret is neither stored here nor given a default. The singleton insert is atomic, so only the first successful onboarding can create the account. Sessions are extended only while active and unexpired; the API issues the opaque token only in an HttpOnly cookie. The store has no deletion operation, and `jarvis_app` cannot delete owner/session rows; expired rows require a separately authorized maintenance policy.

The auth store and schema are implementation foundations, not proof that a database migration has been applied to a deployed service. See the API's framework-neutral session boundary; no running API listener or Colima deployment is qualified by these package tests.

## Owner project allowlist

`PostgresProjectConfigStore` reads project rows and their current immutable configuration version only from the internal `jarvis` schema. Repository IDs cross the API as canonical decimal strings and have a global unique index; repository owner/name are mutable display metadata, never the authorization key. Adds require an existing active installation row and an already activated core policy, but installation state alone does not create an allowlist entry. Initial policy/profile references are injected from trusted core configuration, not accepted from repository, model, GitHub-installation, project-mutation, or request content. The public API returns only the internal project identity, lifecycle state, and config version; it does not return policy hashes, profile references, or credentials. No unaccepted provider, permission, limit, or skill-consent configuration schema is introduced.

Owner add/update/remove operations lock the project identity, compare the expected config version, append an immutable `project_config_versions` row, update the project projection, and insert an actor-attributed, insert-only audit event in one transaction. Removal marks the project `removed` and retains request/configuration history. The same project-row lock serializes these changes against request admission and clarification revalidation; a removal or stale version cannot create a task, queue entry, or outbox event. The request authorization adapter resolves only current internal project/configuration rows and fails closed for missing or ambiguous identities. No skill-consent mutation or automatic repository/issue/Dependabot ingestion is provided here.

These are framework-neutral API and persistence contracts, not a mounted listener or deployed configuration service. Existing synthetic policy/profile references do not qualify a real provider or GitHub installation; D02/D03 and applicable deployment/review gates remain live-operation prerequisites.

## Durable queue

`PostgresQueueStore` persists queue admission only for a task already created by the core and still bound to an active, authorized project, queued request, current configuration and policy. Its unique event/task keys make replay idempotent and reject identity reuse with changed scheduling parameters. Claims use PostgreSQL row locks with `SKIP LOCKED`, database time, a 60-second maximum lease, attempt history and a strictly increasing fencing epoch. Completion/failure transitions are compare-and-set operations that recheck the current worker, epoch and unexpired lease inside the same transaction as task/request state and outbox updates.

The outbox records idempotent queue transitions. Delivery is at least once; it does not promise a distributed exactly-once effect. An unknown external result is retained as `reconciliation_required` and cannot be claimed again until a core reconciler observes whether the effect happened. Indeterminate reconciliation leaves it pending; only an observed not-applied result can be retried within the task deadline and three-attempt maximum. Task payloads are never copied into the queue or outbox: the queue carries only the identifier of an already durable core task, and outbox events contain bounded transition identifiers only.

Plan and development completion persists the schema-versioned canonical result in `task_results` within the same transaction as lease-fenced queue completion. The queue stores the result UUID reference, not the result payload. The closed envelope carries core request/task/attempt/lease/mode/revision/provider/model attribution; plan citations must match the trusted snapshot binding, while development payloads remain inert/untrusted. `PostgresTaskResultReadModel` joins the result to a succeeded queue row and an active owner project; the API exposes it through the owner-authenticated `GET /api/v1/tasks/:id/result` boundary. D09's 90-day report retention applies to result rows. Privileged purge and encrypted-backup enforcement remain J05 work and are not implemented or qualified by JV-302; real result persistence must not be activated before that gate. This is storage/read-contract implementation only, not provider dispatch, patch application, or publication.

The queue package exposes an injected `QueueStore` port and deterministic service logic; it has no production in-memory fallback or external integrations. PostgreSQL concurrency and lease-expiry behavior require the real integration test. Provider/Docker lifecycle, production dispatch, startup reconciliation, and deployment remain unqualified.

## Checkpoints

`saveCheckpoint` accepts only the closed, bounded core-state shape, binds it to its task configuration and policy, and writes only when the task/project/installation are active, the specified attempt owns the current unexpired lease epoch, and every exact skill revision remains approved under the task configuration. Unique task/attempt/epoch/step keys prevent duplicate checkpoints. `loadLatestCheckpoint` rechecks project, installation, configuration, and exact skill consent; callers must create a new lease and revalidate all external evidence before resuming work. A missing checkpoint is not evidence that a task is authorized.

Skill-consent decisions receive a database-assigned, strictly increasing order per project while holding the project-row lock. Authorization compares this order rather than caller-controlled `decided_at` timestamps or random UUIDs, so backdated or equal timestamps cannot make a later revocation ineffective. Migration `002_skill_approval_order` backfills existing decisions deterministically by `decided_at, id` and initializes each project's counter to its greatest assigned order.

Checkpoint data contains bounded identifiers/digests and stable reason codes, never prompts, plans, patches, credentials, or provider session state. Plans and review reports have separate immutable tables; task results are separately lease-bound and immutable to the runtime role. The checkpoint interface is not wired into API/worker lifecycle or a live JARVIS database yet; migration and adapter tests alone do not qualify restart recovery or product operation.

## Verification

Run `pnpm --filter @jarvis/contracts run test`, `pnpm --filter @jarvis/queue run test`, `pnpm --filter @jarvis/worker run test`, `pnpm --filter @jarvis/api run test`, `pnpm --filter @jarvis/persistence run typecheck`, and `pnpm --filter @jarvis/persistence run test`. The `Repository configuration` job in the repository-checks GitHub Actions workflow runs persistence integration tests against its fresh PostgreSQL 18.6-bookworm service, using the immutable image digest and fake job-local credentials; this makes real migration/transaction coverage part of blocking CI for pull requests, pushes to `main`, and manual dispatches. JV-302 coverage checks plan/dev envelopes and, when `JARVIS_TEST_DATABASE_URL` points at an exclusively used empty disposable database, atomically stored queue/result references and owner-scoped reads. The service is scoped to that job; other workflow jobs do not use it. No database secrets or persistent/self-hosted database are used.

For a local real PostgreSQL integration run, set `JARVIS_TEST_DATABASE_URL` to an exclusively used, empty disposable database whose name begins `jarvis_issue8_`. The test applies all migrations, checks that application tables are empty, holds a database advisory lock, and commits its fixture. It covers checkpoint authorization; queue duplicate intake, exclusive claims, lease-expiry recovery, monotonic fencing, stale completion rejection, uncertain external outcomes, reconciliation and atomic outbox/task state; and request-intake authorized admission, duplicate and concurrent replay, clarification, and legacy-row safety. Before cleanup it locks all application tables and fails closed unless their row counts still exactly match the fixture; it truncates the `jarvis` application tables without `CASCADE`, so an unexpected foreign-key dependency in another schema prevents cleanup rather than deleting that schema's data. Run the additional role/schema-scope fixture by streaming it into the pinned PostgreSQL container through the dedicated context: `docker --context colima-jarvis exec -i "$task_postgres_container" psql -U "$task_database_user" -d "$task_database" -v ON_ERROR_STOP=1 < packages/persistence/test/schema.integration.sql`. Never rely on the globally selected Docker context. For local tests, use the repository's pinned PostgreSQL image on the dedicated `colima-jarvis` profile; unit tests without the URL use a fake pool and do not replace database integration or restore qualification. Do not run repository-provided commands from an analyzed product project until its separate execution policy is accepted and qualified.
