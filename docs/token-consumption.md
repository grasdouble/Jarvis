# Token consumption and usage accounting

**Status: bounded gateway accounting and exact OpenCode per-dispatch runtime corroboration are implemented; overall #301 acceptance remains incomplete and production dispatch remains disabled.** The gateway assigns each dispatch a stable UUID, persists its intent, and returns it in `x-jarvis-dispatch-id`; a JARVIS-image-owned OpenCode HTTP-response plugin reads only allowlisted numeric usage and reports it through the authenticated loopback bridge, gateway UDS, and API-owned accounting UDS. PostgreSQL binds the runtime observation to that exact persisted operation ID, stores it as non-additive corroboration, and keeps gateway usage canonical. Startup marks unfinished gateway intents unknown. OpenCode project config/plugin discovery is disabled at startup; the only configured plugin comes from the trusted runtime image. Repository tests cover propagation, sanitization, replay and mismatch rejection. The pinned OpenCode 2.0.32 ARM64 synthetic Colima path passed plugin suppression, UDS dispatch/response/correlation, environment/symlink and permission probes, and clean shutdown; the persistence integration suite passed against an isolated disposable PostgreSQL 18.6 database. Deployed Compose, live provider/egress no-bypass qualification, PostgreSQL-backed CI, and production dispatch remain unverified/disabled.

Issue #301 does not add money reservation or enforcement. The owner-selected D02/D05 boundary is controlling: trusted configuration selects exactly Copilot or OpenAI, with no automatic failover; provider subscriptions/credits stay provider-managed. JARVIS does not access billing/admin APIs or credentials, poll quotas, or infer balances, invoices, charges or costs. Only allowlisted usage returned through ordinary request traffic is eligible for observation; missing, incomplete or interrupted outcomes remain unknown. No prompt, code, response, reasoning content or secret is persisted.

Older cost, reservation, pricing, billing-reconciliation and monetary-ceiling examples below are historical requirements, not authorized behavior. The implementation leaves legacy financial columns unused and null; their existence does not mean accounting or enforcement is active.

## Scope and ownership

Future usage observation may cover each model request dispatched by JARVIS, including retries and optional digest generation; a missing observation remains unknown rather than zero. Future author/reviewer agents, context compaction, conversations and self-improvement use the same observation rules when delivered; their existence here creates no MVP requirement. Preserve request/provider/model attribution and supported usage returned by normal traffic; tool fees, monetary cost, provider balances and invoice totals are outside this scope.

The delivered API/gateway path persists versioned OpenAI-compatible JSON/SSE usage and ordinary OpenAI response-header quota signals; Copilot provider usage remains unknown unless qualified. A trusted OpenCode HTTP-response adapter receives the gateway's UUID in `x-jarvis-dispatch-id` and sends only allowlisted numeric fields through the existing authenticated bridge → gateway UDS → API UDS path. The API persists this as source `runtime`, matched only by exact operation ID. Runtime rows are corroborative and non-additive: canonical totals are built only from source `gateway`. Missing, malformed, replayed, or unmatched runtime evidence never invents usage or associates with another dispatch. No agent receives an API/DB/UDS route or a new credential; the adapter reuses the bounded per-attempt gateway capability. Startup recovery marks unfinished gateway attempts unknown.

JARVIS tracks only its own controlled traffic. It cannot infer token usage for unrelated local OpenCode sessions, this contributor chat or outside account users, nor infer shared-account charges/invoices from JARVIS observations.

[J10 duration forecasting](duration-forecasting.md) may reuse timestamps and qualified model/profile/effort observations after MVP delivery. Forecasts are separate advisory records, never authority for provider selection, monetary spending or deadlines. Future measurement/calibration cannot turn estimated or unknown usage into reported data.

## Per-request record and token semantics

The gateway persists intent before dispatch. Each gateway invocation receives a distinct UUID `operationId`, returned as `x-jarvis-dispatch-id`, and a dispatch-attempt number; each persisted model request has its own database `id`. Retries that reach the gateway create separate model-request rows. The runtime observation must carry that exact UUID and is stored under the corresponding model request; timestamps, sessions, provider request IDs and attempt aggregates are never correlation substitutes. An interrupted or absent final outcome remains dispatched/unknown; hidden retries prevent claims of complete request coverage.

| Field group | Required meaning |
| --- | --- |
| Identity and attribution | request/operation IDs; owner and optional repository, PR, task, attempt; purpose; provider, requested/resolved model, profile version; dispatch/completion UTC times |
| Future attribution | Optional agent/role, parent execution, conversation/turn or campaign identifiers only when those features exist; each request retains its own observation history |
| Token counters | `inputTotal`, `outputTotal`, `cacheReadInput`, `cacheWriteInput`, `reasoningOutput`: nullable nonnegative integers with per-field `reported`, `unknown` or `not_supported` status and normalization version |
| Evidence | Allowlisted usage and opaque correlation metadata actually returned through normal provider/runtime traffic; source, observation ID/revision, timestamp, mapping/coverage limitations; no prompt, response, reasoning text, billing/admin data or inferred values |
| Financial fields | Not authorized by D05: no monetary reservation, pricing/valuation, charge, balance, invoice or provider billing/admin read |
| Lifecycle | prepared, dispatched, succeeded, failed, cancelled or unknown; observation completeness is separate from task success |

Canonical input/output totals include cache/reasoning subsets only where a qualified adapter can establish that relationship. Preserve supported breakdowns, not additional amounts to add to those totals. If a provider reports mutually exclusive components, a future adapter may derive a total using a tested mapping; if overlap or coverage is unclear, leave the affected total unknown and retain supported components. Never sum five counters indiscriminately. No token estimate or monetary value is inferred. Unknown and unsupported are distinct from an observed zero; report coverage per counter.

Keep observed tokens grouped by provider/model and normalization semantics, with missing components visible. Cross-model counts are operational quantities, not equivalent work or comparable quality. Context-window occupancy is distinct from accumulated observed tokens. Do not store reasoning content to measure reasoning tokens.

## Collection, reconciliation and duplicate protection

1. The trusted gateway persists intent and a dispatched lifecycle transition before calling the configured filter. The selected-provider route and request/token/context/time bounds remain distinct from any monetary control.
2. Period attribution is anchored to the immutable persisted dispatch instant, using half-open intervals (`start <= dispatched_at < end`). A later observation or correction updates the canonical observation for that same request and period; it does not move the request to observation time or create a second usage record. No period aggregation/query is currently implemented.
3. The trusted OpenCode HTTP-response adapter reads the dispatch UUID attached to the corresponding gateway response and reports allowlisted numeric usage only. The gateway forwards it over the authorized accounting UDS; the API binds it to exactly one persisted operation ID. Missing or mismatched IDs are rejected and runtime coverage remains unknown. Hidden retries/compactions that cannot be observed prevent claims of complete request coverage.
4. Persist runtime evidence under a stable per-dispatch observation key. Duplicate reports/replays are idempotent; the OpenCode adapter reports one final cumulative snapshot rather than summing response events. Gateway and runtime sources never add together; `usage_ledger` remains derived only from the canonical gateway observation.
5. Gateway/runtime observations for the same request are non-additive corroboration. Retain source, freshness and conflicts; do not turn token counts into charges, balances, invoices or quotas.
6. Persist permitted observations transactionally. Validate exact schemas, numeric bounds and dispatch identity; unsupported, missing and unknown values remain explicit. Runtime observations do not advance lifecycle state or refresh canonical totals.
7. On restart or stream loss, unfinished gateway intents remain unknown. Missing runtime reports do not imply zero; this adapter does not recover an absent per-call response after process loss.

Runtime observations are untrusted inputs. The bounded loopback bridge keeps the attempt capability in its trusted root-owned entrypoint and injects it only on the gateway UDS callback; the OpenCode child runs as UID 10001 without that environment variable, and cannot read the root-owned supervisor environment, including through a project symlink to `/proc/1/environ`. The trusted parent uses the socket-owning GID to reach the gateway UDS, which is explicitly group-writable but not world-accessible (0660). The container drops all capabilities except SETUID, SETGID and KILL: the first two allow the trusted UID transition; KILL permits forwarding container shutdown to the UID-10001 child. With `no-new-privileges`, no network, and read-only root filesystem, the agent's permission profile still denies shell, and candidate project plugin/config discovery stays disabled. The report route is limited to exact-dispatch usage submission; persistence verifies the operation exists and stores no unmatched evidence. The configured adapter path is baked into the trusted image; the API accounting socket is not mounted into the sandbox.

## Limits and provider-managed charges

JARVIS enforces no monetary reservation, ceiling or spend control under the owner's D05 decision. Provider subscriptions/credits and any account quotas remain provider-managed; JARVIS does not provision billing/admin credentials, query billing APIs or poll quota. Record only supported usage/quota returned by normal provider/runtime traffic, with provenance, observation time/freshness and explicit unknown/unsupported state. No balance, invoice, price or charge is inferred.

Request, token, output, context and deadline bounds remain distinct runtime safety controls. The delivered #301 path attributes bounded OpenAI-compatible JSON/SSE usage and normal-response rate-limit headers only when supported by the selected provider mapping. Missing/malformed evidence remains unknown; unsupported provider fields remain not-supported. No monetary fields, billing sources or provider-account control-plane integration are authorized.

## Query API, UI and daily digest

Proposed read-only routes use the existing owner session and authorization filters:

| Route | Result and constraints |
| --- | --- |
| `GET /api/v1/usage` | Summary of actually observed provider/runtime usage by period/provider/model/purpose and authorized repository/PR/task; finite time range, IANA zone, validated closed filters and bounded group count; no monetary valuation |
| `GET /api/v1/usage/requests` | Cursor-paginated request details and provenance/status, maximum 100 rows per page; bounded time/filter scan; no raw model content or credentials |

Responses may expose inclusive/exclusive period bounds, aggregation watermark/version, missing request/counter counts, token breakdowns and source/freshness. Exact high-cardinality identifiers stay in SQL detail queries and authorized traces, not metric labels. Repository/task filters are checked against stored ownership; arbitrary identifiers are not authority. Queries return only retained data and disclose retention gaps. No monetary reservation or spend totals are returned.

Issue #307 provides deterministic synthetic cross-layer evidence for the existing project dashboard read path, not the proposed `/api/v1/usage` or `/api/v1/usage/requests` endpoints. The integration configures both `copilot` and `openai` profiles, explicitly selects `openai`, and sends only that provider/model through the configured gateway and synthetic in-process filter. Gateway observations reach real disposable PostgreSQL through the API-owned accounting Unix socket. The test exercises a PostgreSQL-backed queue lease and lease-fenced canonical TaskResult completion, then reads the result and persisted usage through owner-scoped API boundaries. It also verifies that a separately dispatched retry has its own operation/usage identity and that replaying the same observation is idempotent. The owner-scoped JSON response from `GET /api/v1/dashboard` exposes only allowlisted quota `source`, `provider`, `mappingVersion`, `observedAt`, `freshness`, and the four request/token limit/remaining counters and coverage statuses; the synthetic fixture and injected authorization boundary do not qualify production authentication, provider dispatch or egress.

The dashboard projection is bounded to the latest 100 model requests per project and latest 100 observations per model request; total request counts and omitted-request metadata disclose request truncation. It is not a daily or period aggregate: no daily usage aggregation/query is implemented. Exposed quota signals come only from allowlisted provider response headers on ordinary request traffic; missing or unsupported quota fields remain explicit. The read path includes owner-scoped request/task/attempt attribution and returns no other owner's project data. No billing/control-plane API, quota polling, balance, charge, or invoice is involved; missing token components remain unknown rather than inferred.

The future usage view can support global → repository/PR → task/attempt drilldown, provider/model/purpose comparison, daily/monthly trends, cache breakdown and failed/abandoned-request coverage. Direct and inclusive parent/child totals are labelled; never add an inclusive parent to its children. Consumption may inform an improvement hypothesis, but fewer tokens never proves quality gains or authorizes a model/profile switch.

Daily digests may summarize actual usage observations and their provenance, including failed/cancelled/unknown requests, with period/correction watermarks. They do not reserve a monetary allocation, include charges or monetary alert thresholds, or infer an invoice. Provider billing/usage observations not returned on the normal request path are excluded.

## Retention, privacy and recovery

Use the existing D09/D11 retention/deletion and restore policies; do not select new durations here. Usage storage contains counters and opaque attribution, not code, prompts, tool bodies, secrets or personal reasoning. Keep only allowlisted metadata and bounded identifiers; ordinary logs redact credential-bearing headers and provider payloads. External telemetry remains off by default. A usage UI is not permission to expose a conversation or another repository.

Deletion purges forbidden identifying content/links under the accepted lifecycle; any retained aggregate or audit fact must be content-free and permitted by that policy. Restore reconciliation applies deletion markers and stop epochs before exposing data or dispatching work. Missing post-backup observations remain an explicit coverage gap; no monetary exposure or budget state is inferred from the restored usage record.
