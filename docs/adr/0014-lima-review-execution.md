# ADR-0014: Isolated Lima execution for contributor review

- Status: Proposed
- Created: 2026-10-27
- Decision owner: Owner
- Requirements and scope: Issue #214 authorized evolution; reviewer-side destructive persistence validation only
- Related Dxx / legacy ADR / issue / PR: Issue #214; PR #275

## Context and decision needed

Issue #214 authorizes candidate code to run only inside a fresh per-run ARM64 Linux Lima VM on this Mac, with PostgreSQL owned by that VM. This replaces the existing local-validation assumption for this scope: the current persistence validation helper executes candidate code on macOS and uses `colima-jarvis`. The authorization does not establish that Lima 2.2.1 can provide the required deny-all network boundary, safe provisioning, or identity-safe teardown.

The exact candidate snapshot must be revision-bound and immutable. Candidate repository code, package configuration, scripts, and outputs are untrusted. No host mounts, forwarded agent, host Docker/Colima socket, ports, secrets, or guest reachability to Mac/LAN/Internet/other runs are permitted during candidate execution. PostgreSQL and ephemeral credentials must remain guest-local. GitHub-hosted workflow checks remain a separate evidence source.

## Options and trade-offs

1. Continue host/Colima execution: rejected for this issue because it contradicts the authorized boundary.
2. Use a fresh Lima VM with a trusted launcher and prove all isolation/cleanup requirements: owner-authorized direction; the Stage 1 bootstrap is implemented and mocked, while full qualification remains outstanding. This costs provisioning and platform-specific acceptance work.
3. Do not execute candidate code locally until qualification is complete: safe current behavior, but leaves local destructive integration evidence limited.

## Decision and rationale

The owner selected a two-stage qualification path for this issue (2026-10-27). Stage 1 may deliver and merge the bootstrap after required human review and ordinary native gates, but candidate execution remains unqualified and unavailable without both explicit Stage 2 operator opt-in and a complete qualification report. Issue #214 remains open/Blocked until Stage 2 runs from the merged trusted-base launcher and passes actual Lima qualification. This ADR remains Proposed pending its applicable formal review/adoption gates; owner direction is not being treated as unaccepted. No host networking helper or persistent host setting is authorized by this record.

## Consequences and verification

The existing `scripts/run_persistence_validation.py` must not be used for this candidate: its implementation runs the candidate on macOS and provisions PostgreSQL using `colima-jarvis`. Mocked lifecycle tests can verify launcher logic but cannot establish Lima, host/LAN/Internet denial, or cleanup behavior. Coordinator-reported manual feasibility evidence (recorded in the issue-delivery ledger at `/private/var/folders/lm/8ls2plln5cjcwxf4v_jbgtpc0000gn/T/opencode/jv-214-ledger.md`; no durable raw transcript is available) describes Lima 2.2.1 with VZ Ubuntu 24.04 ARM64. It reportedly preserved host-initiated `limactl shell/copy` while denying new guest egress using a guest nftables firewall: INPUT allowed loopback, established/related traffic, and TCP/22 only from 192.168.5.2; OUTPUT allowed loopback and established/related traffic only; forwarding and all other new output were denied. Unprivileged probes to a host-loopback canary, Mac LAN/gateway, public IPv4, and IPv4 DNS were reported blocked (EPERM); IPv6 had no route. The reported probe used `--plain --mount-none`; effective settings had no mounts/ports and `ssh.forwardAgent:false`, but `propagateProxyEnv:true`, which a real profile must explicitly disable. The first probe attempt omitted established/related OUTPUT and failed; that rule error was corrected for the reported probe. This is limited feasibility evidence, not qualification: it does not demonstrate a trusted controller, candidate execution boundary, complete control-plane denial, lifecycle cleanup, or full IPv6 isolation.

A later direct reviewer validation used a fresh `jarvis-issue214-run-20261027b` VM with the same bounded ARM64/VZ/no-mount profile and `propagateProxyEnv:false`. The installed nftables rules had default-drop INPUT/OUTPUT/FORWARD; only loopback, established/related flows, and new TCP/22 from `192.168.5.2` were allowed. Fresh host-initiated SSH succeeded. As the unprivileged guest user, new TCP probes to host `.2:22`, the Lima host-agent forwarding port, the guest gateway, public IPv4, and IPv4 DNS timed out; a public IPv6 probe returned network-unreachable, and the guest had no IPv6 default route. The guest user could not flush/change nftables (`Operation not permitted`). This probe did not exercise a host-loopback canary service or a second live instance, and does not establish full cross-run or IPv6 isolation. Exact sanitized results are in `/private/var/folders/lm/8ls2plln5cjcwxf4v_jbgtpc0000gn/T/opencode/jv-214-validation-evidence.md`.

At exact B/H, the persistence test command was run only inside that guest as an unprivileged user, against guest-local PostgreSQL 18.6 from the trusted digest. The scripts-disabled frozen candidate install was offline from the trusted-base lock-derived store. `pnpm --filter @jarvis/persistence test` returned 40 pass, 0 fail, 1 unrelated skip; both required stop-control scenarios passed and were not skipped. The separate `JV-265` restore-gate case remained skipped because its additional service/URL was not configured. The existing mocked runner suite passed 29 tests in the guest after an initial environment-only Node-PATH failure; the new Lima-profile helper suite passed 7 mocked tests after correcting one test expectation. Those earlier checks predate the Stage 1 launcher implementation and therefore did not cover its lifecycle; they also do not establish live Lima qualification.

One earlier disposable setup attempt used `pnpm fetch` and unexpectedly ran an `esbuild` postinstall despite the environment setting. No candidate snapshot was present; that exact VM was firewalled, stopped, and deleted. The successful run used a fresh VM and `pnpm install --frozen-lockfile --ignore-scripts`, with the candidate install separately offline. This incident is recorded because the setup path must use the explicit scripts-disabled install command, never `pnpm fetch`.

Qualification must use synthetic targets/canaries and directly establish, among other acceptance cases: exact B/H snapshot integrity; ARM64 guest; no mounts, agent forwarding, host sockets, ports, secrets, or guest manager control; Mac/LAN/Internet denial including IPv4/IPv6 and aliases/forwarded listeners; no cross-run reachability; unprivileged execution; guest-local PostgreSQL; bounded resource/time/process behavior; concurrent-run isolation; and exact-resource cleanup after success, failure, timeout, and interruption. The Mac probe must discover the active default-route interface and its assigned IPv4 on the trusted host, validate it as a safe unicast target, and bind a separate synthetic canary there in addition to Lima's host-endpoint canary. The guest must directly probe both addresses/ports, report distinct evidence, and reach neither; qualification report production and consumption require both probes and zero accepted connections. An inability to discover or bind either target fails closed. A connection-refused response alone is reachable, not denied; denial evidence requires the guest's observed default-drop firewall and zero canary accepts. No host configuration change is permitted. Where IPv6 has no route, record and prove route/firewall state without claiming a full IPv6 isolation test. If Lima cannot provide the boundary without privileged host-networking or persistent/system changes, stop and retain the local runtime check as limited. GitHub-hosted CI is distinct and does not prove this local acceptance.

## Acceptance and history

The owner selected Lima for this issue; that direction is authorized, but this ADR remains Proposed pending its formal review/adoption gates. The source now includes a candidate-free `--qualify-only` producer, but it has not been validated on this revision or run from the merged trusted base. No Stage 2 qualification evidence exists. Candidate execution remains disabled until the merged producer records successful actual probes and exact teardown.

## Follow-up

The launcher implements a trusted-base candidate-free qualification producer and a separate opt-in candidate path. Mocked tests can establish code-path/report validation behavior only; they do not prove the live Lima network/control-plane boundary or cleanup. Stage 2 must qualify from the merged trusted base before candidate execution is enabled. Do not treat this proposal, source implementation, or a mocked test result as qualification or activation.
