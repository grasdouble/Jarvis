# Bounded self-improvement campaigns

Design status: owner-selected J07 product behavior, specified by [JV-059](https://github.com/grasdouble/Jarvis/issues/59) and implemented later through [JV-051](https://github.com/grasdouble/Jarvis/issues/51) and its children. This document installs no runtime, branches, GitHub rules, credentials or deployment service. D13 still requires accepted experiment and rollout profiles before those actions.

The stable released JARVIS coordinates one bounded improvement hypothesis on a temporary candidate branch. It can integrate eligible task PRs there through the trusted controller, but **every promotion of self-improvement into main requires current human approval**, including routine code changes. Activation requires separate explicit authorization. This product mode does not replace the ordinary contributor workflow or general autonomous-delivery routine-merge policy; JV-051–JV-055 implement its machinery using the contributor workflow.

## Campaign scope and ownership

A campaign has a stable identifier, one hypothesis, measurable gain and quality/security guardrails, one durable proposal, permitted internal task slices, and owner-authorized limits on scope, cumulative attempts, elapsed time, spending/resources and change size. Values must be accepted in D13 rather than invented by an agent. Missing limits prevent execution. Rejected, abandoned and inconclusive campaigns retain dispositions and consumed budgets; starting another child, repair branch, worker or process cannot reset them.

Use a temporary branch such as `improvement/<campaign-id>` created from a recorded target-main revision. Do not use an indefinitely growing branch per JARVIS instance. Each internal task has its own branch, qualified sandbox/workspace, acceptance and PR targeting the campaign branch; it needs no GitHub issue or milestone. The ordinary contributor issue workflow still governs development of the mechanism itself. A worktree organizes Git state and is not a security boundary: task execution still uses the qualified Colima isolation profile, without Mac mounts, Engine socket or publication credentials.

The durable core claims the campaign, branch and child tasks with exclusive ownership and fenced leases. Serialize writes to a campaign branch; the remote head precondition and a current fencing check reject stale dispatches. Already accepted remote operations cannot be recalled reliably and must be reconciled before ownership is released. Concurrent campaigns require an explicitly qualified overlap/resource policy; otherwise a conflicting claim waits or hands off. Quotas include retained candidate resources so review waiting cannot accumulate unbounded sandboxes. No candidate service runs with production authority merely because code reached the campaign branch.

## Operational tracking and proposal intake

Track an actual improvement directly in a detailed **main-promotion PR** labeled `self-update`, with project membership. No operational root issue, child issue, JV key or milestone is required. **J07 — Self-improvement** and JV-051–JV-055 continue to track building the capability under the ordinary contributor workflow. The [Self-update table](https://github.com/orgs/grasdouble/projects/1/views/7) filters `repo:grasdouble/Jarvis is:pr label:self-update`; it shows all states for audit, including linked superseded/abandoned PRs. A filter does not import repository PRs into the project: the controller adds and verifies every promotion item. Technical task/repair PRs are linked in the promotion manifest and do not receive `self-update` unless they become the canonical main-promotion PR.

Persist a sourced, deduplicated proposal and obtain authorized scope/limits before candidate work. A PR requires a real diff: retain rejected/deferred or pre-patch proposals in the durable ledger and UI/digest instead of creating empty PRs or substitute issues. Once real candidate changes exist, create or reuse one draft promotion PR against main, add the label/project item and maintain its body as evidence develops. Keep it draft while implementation, comparison or required independent review is incomplete; a draft is not merge eligibility. Preparing a pre-patch proposal does not require a PR identity, so intake and candidate startup cannot deadlock on publication.

Use the [PR content contract](../skills/jarvis-self-improvement/references/proposal.md) for browser and programmatic publication: problem/provenance/window, one hypothesis, measured baseline versus desired gain and quality/security guardrails, scoped changes/dependencies, actual verification/comparison/uncertainty, limits/decision owner and risks/stop/recovery. Include internal proposal/campaign identity, task manifest, current revisions and distinct promotion/activation states. Core validates the same content regardless of client and reads back native PR identity, base/head, label and project membership. Incomplete evidence is explicit; no label, draft state, template or manually set project status grants execution or promotion authority. Pin actual repository/label/project/view IDs in trusted configuration; reconcile deleted/renamed/drifted metadata before affected effects rather than creating duplicates. No dedicated operational milestone is needed.

Enforce durable repository-scoped proposal key → campaign → at most one active promotion PR mappings using native IDs, not editable titles/labels. Reconcile inventories and uncertain remote outcomes before retries; timeout, restart or PR replacement cannot create a new campaign or budget. A different hypothesis needs a separate proposal/campaign/promotion PR. Technical task PRs may be multiple, but a promotion cannot bundle unrelated improvements. Conflict repair may close/supersede the old promotion and create one linked replacement under the same campaign; an unknown prior outcome stops replacement until reconciled. Historical PRs retain label, evidence and supersession links. The controller reconciles externally created duplicates into a hold/needs_human state rather than selecting both. Neither project filtering nor GitHub alone enforces this uniqueness.

These source files are separate from contributor skills under `.agents/skills/` and deliberately outside OpenCode's current discovery locations. This change installs no plugin, loader, SDK adapter or global skill; the v0.1 read-only PR-review profile must not load repository skills or configuration automatically.

The future J07 adapter supplies the selected profile only from trusted controller configuration, validates its schema and pins its identity/version/digest in the attempt context. Bundle and profile are read-only. The profile describes repository/branch conventions, tracking records and content/result contract versions. It cannot grant permissions, writable scope, budgets, thresholds, approval, publication, merge or activation. Those remain in controller-owned mission/policy inputs. Candidate `.opencode`, `.agents`, `.claude`, home content, repository profile copies, duplicate names and symlinks cannot substitute the pinned bundle or profile. Verify actual loading and exclusion behavior against the pinned OpenCode version; if trust cannot be established, do not enable the profile.

The skill returns proposals, bounded patch/result artifacts and structured effect intents through the controller contract; it never obtains credentials, calls contributor helpers, approves, merges or activates itself. No new callable handler is implemented here. Core validates intake, claims, limits, publication, evidence and gates outside model output; reviewers/evaluators remain independent attempts. Edits to a candidate skill or profile do not replace the active trusted procedure, profile or evaluator. D13 and JV-053/JV-054 accept schema/profile/loader/tool contracts and numeric limits before enabling work.

## Trust and promotion gates

| Role or target | Allowed scope |
| --- | --- |
| Stable controller | Select only authorized proposals; retain trusted policy, ledger, credentials and remote-effect intents outside candidate write scope |
| Candidate author | Produce a scoped patch in its own task sandbox; no GitHub/deployment credentials or writes to the running controller/evaluator |
| Independent reviewer | Read the exact snapshot and sanitized criteria/evidence; author none of the candidate or conflict fixes; cannot publish or approve itself |
| Trusted evaluator/executor | Pin the protocol, holdouts, environment and comparable workload outside candidate control; execute only qualified credential-free tests |
| Campaign integration | Controller merges a child only with authorized scope, current CI and independent review; sensitive/unknown child changes retain the existing human gate |
| Promotion to main | Full campaign evaluation, full diff review, current CI/native protections and explicit human approval of this promotion are all required |
| Activation | Separate immutable artifact/config/environment authorization and qualified rollout/recovery profile; merging source never hot-reloads JARVIS |

Candidate changes to CI, skills, prompts, policy or tests cannot redefine the trusted gate used for that campaign. Human approval of a sensitive proposal does not cause its candidate policy to become the live controller policy. Any eventual trusted-policy replacement has its own approved activation path. Tests and branch workflows must not expose production secrets or execute candidate code with a privileged event/token. GitHub protections must cover main and campaign targets appropriately without an App bypass. Branch-specific CODEOWNERS are evaluated on the PR's base branch; the controller additionally classifies changes under trusted released policy, so an editable campaign copy cannot silently remove a gate. These are qualification requirements, not claims that rules are configured today.

## Lifecycle and delivery accounting

1. Deduplicate an evidence-backed proposal, obtain scope/limits, claim the campaign and pin its inputs. Record target main `B` separately from the stable deployed incumbent `S`; main may contain changes that have not been activated.
2. Define bounded internal task slices with measurable acceptance and manifest dependencies. Publish each child PR against the campaign branch after its actual verification and independent review.
3. Reconcile and confirm child merges through the controller. Maintain a manifest mapping internal tasks/PRs to their original and integrated revisions, with finding dispositions and evidence digests. A squash merge must not erase this traceability from the ledger.
4. Freeze admission when the hypothesis is implemented or a campaign limit is reached. Do not append unrelated improvements while waiting for a human. A failed limit stops/hands off rather than forcing promotion.
5. Compare the exact assembled candidate `H` with deployed incumbent `S` under the fixed protocol and run compatibility/regression checks for target `B`. Include all failed attempts/costs; inconclusive or rejected evidence cannot become promotion eligibility.
6. Update the existing draft promotion PR from the frozen candidate branch to main, or create it once a real diff exists; maintain at most one active promotion; retain linked superseded PRs as history when remediation needs a new head branch. Present the complete diff, child manifest, baseline/candidate measurements, uncertainty, independent assessment, current target revision, migration/recovery implications and separate activation status.
7. Obtain authenticated human approval bound to the promotion digest: repository/target, `B`, `H`, policy/protocol/evidence versions and manifest. Preserve all native required approvals and checks; a model verdict or copied comment cannot supply human authority. Any relevant change invalidates internal eligibility even if GitHub retains an approval. Never infer promotion permission from a previous child's approval.
8. Recheck revisions, current authority/stop state, native protections, checks and reviews immediately before the expected-head merge request. A changed or unknown target stops dispatch and triggers reconciliation/revalidation; the head precondition alone does not atomically freeze main. The qualified native up-to-date/check controls remain necessary. Confirm the remote merge before recording source delivery; record pending activation separately.

A task merged only into the campaign is `integrated_candidate`, not delivered or Done. Its durable task stage and the promotion PR body retain actual progress; project status cannot certify delivery. Candidate-local prerequisites use verified manifest evidence within the same claimed campaign, never fabricated global completion. An in-progress draft promotion can use In Progress; a complete verified candidate awaiting review uses In Review. A confirmed main merge marks source integration only; activation remains a separate durable state. Closed abandoned/superseded PRs are not successful source delivery, even if native project automation marks a closed item Done; record their disposition and reconcile the projection. Stop on an unreconciled transition rather than acting on the board alone. Operational PRs need no closing keywords or issue, and are excluded from the issue-based Next up queue. Optional references to real contributor issues do not waive those issues' acceptance/milestone rules; close them only after confirmed main delivery and their own criteria.

After confirmed promotion, retire the campaign branch and temporary resources once no review/recovery use remains; preserve evidence and needed work. A subsequent campaign starts from the new main with its own authorization, not by continuing a previously squashed branch. Abandonment preserves the disposition and current main, releases claims and cleans temporary resources; it does not mark undelivered tasks Done.

## Conflict and drift remediation

Remediation is part of the same campaign and cumulative budget, whether Git reports a textual conflict or semantic integration checks fail without one.

1. Freeze child admission and promotion; invalidate promotion eligibility. Record the original candidate `H0`, prior target, latest verified main `B1`, stable incumbent `S`, manifest and existing approvals/evidence. Preserve the PR and record a linked repair episode.
2. Acquire an exclusive, fenced remediation claim. Select the accepted Git strategy below and create a separate repair branch/workspace without resetting main, force-pushing the shared candidate, or rewriting published history. Do not resolve directly in the running service. If the native merge strategy cannot preserve this qualified process, hand off rather than silently change strategy.
3. Resolve using both sides' intent, campaign/task acceptance and trusted policy. Never blanket-select ours/theirs, silently drop a child, weaken the oracle or broaden scope to make checks pass. Ambiguous functional/security intent, incompatible migrations or an out-of-scope change requires a documented human decision; continue only independent authorized preparation.
4. Run regression/integration checks on the full main-to-repaired-candidate diff, refresh the child manifest and compare the resulting candidate with the pinned incumbent under the accepted protocol. If the deployed incumbent or relevant environment/protocol changed, invalidate the comparison and establish a newly accepted comparable evaluation. New measurements and review are required for changed inputs, not relabeled old results.
5. A fresh independent reviewer who authored none of the repairs reviews the complete result and the resolution of both sides' acceptance. Sensitive repair changes require the applicable human gate before branch integration. Publish the repair through its reviewed PR and guarded controller, either integrating it with preserved ancestry or making it the replacement promotion candidate under the strategy below; never inject a direct unreviewed repair commit into the shared candidate. Refresh evidence again for the resulting integrated SHA, especially after squash; a repaired branch's SHA is not the integrated candidate's SHA.
6. Update the existing promotion PR when its head branch can be retained; otherwise link and supersede it with one replacement promotion PR, keeping the same campaign, manifest and consumed budgets. Invalidate prior internal approval and obtain current human approval of the new promotion digest. Native approval retention alone cannot authorize a changed digest. If main or another relevant input moves again, repeat within the same finite limits.
7. Stop on exhausted limits, cancellation/revocation, unresolved intent or unknown remote outcomes. Persist Blocked/needs_human with cause, relevant revisions, next owner/action and exact resumption condition. Reconcile accepted remote effects before retrying. After resolution, record separate linked Unblocked evidence and restore only the verified lifecycle stage; never promote automatically from the comment itself.

### Preserve main ancestry under the permitted merge method

D13 must qualify a concrete strategy against the repository's actual allowed methods; branch update and promotion are not interchangeable operations.

- When merge commits into the campaign are permitted, branch the repair from `H0`, merge `B1` there, and integrate the reviewed repair PR with a method that preserves `B1` as an ancestor. Rebind evidence to the exact resulting candidate.
- For a squash-only repository, start a fresh repair/promotion branch from `B1`, reapply the campaign's manifest-backed changes with explicit conflict resolutions, and review its complete `B1`-to-candidate diff. Keep the original campaign branch immutable for traceability. The new branch becomes the campaign's promotion candidate; create one linked replacement promotion PR if the original head branch cannot be reused without rewriting history. Human approval and all current checks/evaluation apply to the replacement. Do not squash a repair back into the old campaign and assume this preserves main ancestry: it does not. Future child work stays frozen; any follow-up uses the explicitly rebound candidate and serialized claim.

Verify the selected current-main revision is an ancestor of the resulting promotion candidate, as well as checking its semantic contents and native up-to-date rules. Preserve original-to-reapplied mappings, removed/changed children and review evidence; a changed acceptance set requires authorization rather than silently dropping work. Every supersession/replay still consumes the original campaign's limits. Missing qualified strategy or ambiguous replay requires handoff, never enabling another merge method/bypass automatically.

## Durable records and recovery

Extend proposed delivery/experiment records with a campaign manifest: campaign/proposal/canonical promotion IDs and unique repository-scoped mapping; native label/project/view configuration IDs; skill bundle and selected project-profile ID/schema version/digest; internal task/PR and commit mappings; target repository/branch and `B`; incumbent artifact/source/config/schema `S`; assembled candidate `H`; protocol/policy/environment/evidence digests; current claim/fence; cumulative limits/consumption; stop epoch; promotion PR and human approval digest; remote merge result; separate activation intent/result. Persist repair episodes with `H0/B1`, findings, decisions, repaired/integrated SHAs, attempts and dispositions.

Record lifecycle stages such as authorized → assembling → evaluating → awaiting_human_promotion → promoting → integrated_main/pending_activation; synchronization may enter remediating, and limited/blocked/exhausted/cancelled/unknown outcomes stay explicit. Native GitHub state is an external projection, not the authoritative campaign stage. Unique effect keys bind the target/action/revision digest; inbox/outbox, fenced leases and remote rereads handle duplicates, crashes and ambiguous PR/merge results. A success response for one child or queued merge is not proof that the whole campaign reached main. Restart restores budgets/stop/claims and reconciles before any new effect.
