# Changesets

Use Changesets to record intentional versions for the private packages in `apps/*` and `packages/*`. Each starts at `0.0.0`. The private repository root is orchestration only and is not a versionable package.

For a package behavior/API change, run `pnpm changeset`, select the affected packages, choose the deliberate SemVer bump, and summarize the user-visible change. On ordinary source PRs, repository CI runs `pnpm changeset status --since=<PR base>` and checks that at least one Changeset targets a versionable workspace changed by the PR. A Changeset for only an untouched package does not satisfy this check. The gate checks target overlap, not every affected package; authors must still include each package whose behavior/API changes. For a package-scoped documentation, test, or contributor-tooling change with no release impact, use `pnpm changeset add --empty --message "Explain why no package release is needed"` to make that no-release intent explicit to the check. Keep the explanation specific; an empty changeset must never hide a behavior/API change, and it is not needed for changes outside versionable workspaces.

`pnpm changeset status` reports pending release intent locally. To reproduce the PR check, run `python3 scripts/ci/check_changeset_pr.py origin/main` (substitute the PR's base ref when it differs). `pnpm changeset version` consumes release intent and updates package versions, changelogs, and internal workspace ranges; review those changes before committing. Regenerate `pnpm-lock.yaml` with `pnpm install --lockfile-only` when updated workspace ranges make it necessary for the frozen install. The CI gate recognizes only stable generated version PRs whose package bumps match the consumed release entries and valid internal dependent propagation. Workspace-range edits must point to packages released by that plan; lockfile changes are limited to the corresponding importer specifiers, with all other lockfile content unchanged. Source changes, unrelated package bumps, recursive-workspace omissions, and unrelated lockfile edits do not qualify for the exemption. A CI fixture runs the pinned CLI's version command, synchronizes the lockfile and verifies both accepted and rejected generated-PR shapes. Starting at `0.0.0`, a first patch is `0.0.1` and the next patch is `0.0.2`. Choose minor or major deliberately for feature/API and incompatible changes; do not classify every change as a patch. A package version is not the JARVIS product's v0.1 MVP acceptance.

This repository does not publish packages to npm. Private packages are versioned but Changesets private-package tagging is disabled. Do not run `pnpm changeset publish`.

The pinned `Package version PR` workflow consumes pending Changesets on trusted `main` and creates or updates one reviewed `changesets/version` PR. The separate `Package releases` workflow runs only after that branch's PR is confirmed merged into `main`. It validates the generated version-only diff against the PR's first parent, creates immutable annotated Git tags named `<package-name>@<version>` at the exact merge commit, and creates matching GitHub Releases using only that version's section from the package `CHANGELOG.md`. A rerun accepts an existing tag/release only when its commit, name, notes, and release flags match; a conflicting tag or release fails without retagging or rewriting it. If an attempt stops after creating a tag, the next run reconciles that tag and continues with the missing Release.

Both workflows use the owner-provisioned `package-releases` Actions environment. Follow the [step-by-step App and environment provisioning guide](../docs/package-release-app-setup.md). Configure `PACKAGE_RELEASE_APP_CLIENT_ID`, `PACKAGE_RELEASE_APP_SLUG`, and `PACKAGE_RELEASE_APP_INSTALLATION_ID` as environment variables and `PACKAGE_RELEASE_APP_PRIVATE_KEY` as an environment secret. The installed App is limited to `grasdouble/Jarvis`; the version-PR job requests only Contents and Pull requests write access, and the post-merge job requests Contents write and Pull requests read. Do not use the Mac PEM, a personal token, blanket Actions approvals, or a ruleset bypass. Missing or mismatched credentials stop the workflow without fallback. Live run [39314538994](https://github.com/grasdouble/Jarvis/actions/runs/39314538994) verified environment values and App identity, but no versionable Changeset was available, so actual version-PR and tag/Release writes remain unverified; do not manufacture a package release to test them.

Package tags and GitHub Releases are intermediate source-release records, not npm artifacts, product deployments, or proof that the complete JARVIS product passed its v0.1 MVP acceptance gate. A product release must separately identify its exact package/image revisions.
