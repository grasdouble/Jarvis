# Changesets

Use Changesets to record intentional versions for the private packages in `apps/*` and `packages/*`. Each starts at `0.0.0`. The private repository root is orchestration only and is not a versionable package.

For package behavior/API changes, run `pnpm changeset`, select each affected versionable workspace, choose its deliberate SemVer bump, and summarize the user-visible change. On ordinary source PRs, CI requires a Changeset entry for every modified versionable workspace with at least one changed, non-excluded file. Explicit exclusions cover non-release files (for example, tests that are not shipped); a workspace with only excluded changes needs no entry. Empty no-release Changesets do not exempt a workspace that otherwise requires coverage. A deleted package alone needs no Changeset. A changed Changeset targeting a package absent from the PR-head workspace set is rejected; unchanged historical Changesets are not checked, so unrelated PRs need not clean up stale entries. The source-PR gate computes changed paths from the base-to-head diff, then discovers workspace identities only from the exact PR head. The pinned Lufa checker `9e985a3bb7fd2892e1075bed1c87acd4c1f527d8` maps diff-visible paths to those head workspaces; the local validator follows the same head-only rule. Do not rely on `pnpm changeset status` alone for stale-target validation.

For a simplified local check, run `python3 scripts/ci/check_changeset_pr.py origin/main` (substitute the PR's base ref when it differs). This uses default head and exclusion settings; it is not an exact reproduction of CI. See the [full CI reproduction command and configured exclusions](../docs/development-workflow.md#package-versioning-and-releases). `pnpm changeset version` consumes release intent and updates package versions, changelogs, and internal workspace ranges; review those changes before committing. Regenerate `pnpm-lock.yaml` with `pnpm install --lockfile-only` when updated workspace ranges make it necessary for the frozen install. The generated-version-PR exemption remains restricted to validated stable release output, with supported consumed entries, explained dependent propagation, matching changelogs, and only corresponding lockfile importer changes. The trusted release wrapper also validates its complete dirty working-tree output without staging it; ordinary source-PR checks use the committed diff. Starting at `0.0.0`, a first patch is `0.0.1` and the next patch is `0.0.2`. Choose minor or major deliberately for feature/API and incompatible changes; do not classify every change as a patch. A package version is not the JARVIS product's v0.1 MVP acceptance.

This repository does not publish packages to npm. Every versionable workspace is private. The release workflow leaves the pinned Lufa action's default `pnpm changeset publish` command in place: Changesets 3.0.3 excludes private packages from registry lookups/publication and, with `privatePackages.tag: true`, emits local git-tag events for eligible private packages. Do not make release workspaces public or change this configuration to publish packages to a registry.

The `Package version PR` workflow runs from trusted `main` and uses the Lufa `changesets-release` action pinned to `320fce890fbd7bcb347141648174d1c3f7b786ad` (whose nested `changesets/action` is pinned to `ae32849d5ba541f9ae29e40e22a623bc13562f51`). It creates or updates the managed `changeset-release/main` review PR; human review and native branch protections remain in force. The post-merge `Package releases` workflow retains its closed/merged/same-repository/main/recognized-branch filters and checks out the event merge SHA. It no longer runs the former post-merge PR identity/generated-diff preflight or asserts checkout/context SHA equality; release relies on event metadata and protected pre-merge gates. Before invoking the same pinned Lufa action, it creates runner-local fallback `CHANGELOG.md` files for private workspaces lacking one. The Lufa action's default `pnpm changeset publish` then emits private-package git-tag events without npm registry lookup or publication; its GitHub Release handling uses the package changelogs. The workflow does not reconcile existing Releases, and upstream tag failures may be warnings while Release creation continues. These limitations do not weaken human review or native protections.

Both workflows use the owner-provisioned `package-releases` Actions environment. Follow the [step-by-step App and environment provisioning guide](../docs/package-release-app-setup.md). Configure `PACKAGE_RELEASE_APP_CLIENT_ID`, `PACKAGE_RELEASE_APP_SLUG`, and `PACKAGE_RELEASE_APP_INSTALLATION_ID` as environment variables and `PACKAGE_RELEASE_APP_PRIVATE_KEY` as an environment secret. The installed App is limited to `grasdouble/Jarvis`; the version-PR job requests Contents and Pull requests write, and the post-merge job requests Contents write only. Do not use the Mac PEM, a personal token, blanket Actions approvals, or a ruleset bypass. Missing or mismatched credentials stop the workflow without fallback. Live run [39314538994](https://github.com/grasdouble/Jarvis/actions/runs/39314538994) verified environment values and App identity, but no versionable Changeset was available, so actual version-PR and tag/Release writes remain unverified; do not manufacture a package release to test them.

Package tags and GitHub Releases are intermediate source-release records, not npm artifacts, product deployments, or proof that the complete JARVIS product passed its v0.1 MVP acceptance gate. A product release must separately identify its exact package/image revisions.
