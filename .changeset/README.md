# Changesets

Use Changesets to record intentional versions for the private packages in `apps/*` and `packages/*`. Each starts at `0.0.0`. The private repository root is orchestration only and is not a versionable package.

For a package behavior/API change, run `pnpm changeset`, select the affected packages, choose the deliberate SemVer bump, and summarize the user-visible change. On ordinary source PRs, repository CI runs `pnpm changeset status --since=<PR base>` and checks that at least one Changeset targets a versionable workspace changed by the PR. A Changeset for only an untouched package does not satisfy this check. The gate checks target overlap, not every affected package; authors must still include each package whose behavior/API changes. For a package-scoped documentation, test, or contributor-tooling change with no release impact, use `pnpm changeset add --empty --message "Explain why no package release is needed"` to make that no-release intent explicit to the check. Keep the explanation specific; an empty changeset must never hide a behavior/API change, and it is not needed for changes outside versionable workspaces.

`pnpm changeset status` reports pending release intent locally. To reproduce the PR check, run `python3 scripts/ci/check_changeset_pr.py origin/main` (substitute the PR's base ref when it differs). `pnpm changeset version` consumes release intent and updates package versions, changelogs, and internal workspace ranges; review those changes before committing. Regenerate `pnpm-lock.yaml` with `pnpm install --lockfile-only` when updated workspace ranges make it necessary for the frozen install. The CI gate recognizes a generated version PR only when it consists of package version/internal workspace-range updates, generated changelogs, consumed release Changesets, and an optional lockfile update; source changes do not qualify for this exemption. A CI fixture runs the pinned CLI's version command, synchronizes the lockfile and verifies that this generated-PR shape passes the unified gate. Starting at `0.0.0`, a first patch is `0.0.1` and the next patch is `0.0.2`. Choose minor or major deliberately for feature/API and incompatible changes; do not classify every change as a patch. A package version is not the JARVIS product's v0.1 MVP acceptance.

This repository does not publish packages to npm. Private packages are versioned but Changesets private-package tagging is disabled. Do not run `pnpm changeset publish`. Post-merge Git tags in the form `<package-name>@<version>` are reserved for the separate, reviewed release workflow scoped by [issue #35](https://github.com/grasdouble/Jarvis/issues/35); that planned workflow must verify the release commit and handle tag conflicts/idempotently.
